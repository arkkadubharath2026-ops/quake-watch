## Reading the results

- Slowest indexed p95 across all cases: **51.0 ms** (PRD target: p95 < 500 ms for a common filtered query).
- Without indexes every workload is a full collection scan, so its cost grows with the collection; with indexes it grows with the answer. On small datasets a scan is as fast as (or faster than) an index lookup, so speed-ups below 1x at 500-10k are expected; at 100k the indexes win on every workload. The index set is justified at production scale.
- List workloads scan twice without indexes (the count subquery and the page each read the collection); with indexes the count reads index entries only.
- `event_list_latest` has no filter besides `merged_into == null`, so its count still walks every index entry; it stays well inside the target but is the workload that grows with the catalogue.

## Tuning history

The first run of this benchmark found a regression the demo-sized dataset could not show: at 100k records the default list (newest first, page of 25 + total) took **p50 505 ms / p95 611 ms with `qw_events_occurred_at` and 81 / 90 ms without it**, missing the PRD target and losing to a full scan. EXPLAIN showed two causes:

1. The sort `occurred_at, _key` (the `_key` tie-break keeps paging stable) was not covered by the single-field index, so the optimizer kept a SORT node and fetched all 100,000 documents through the index before sorting.
2. The total came from `fullCount`, which makes the page query materialise every matching document just to evaluate `merged_into == null`.

Changes (applied to existing databases by `arango_migrate` drift repair):

- `qw_events_occurred_at` is now `[occurred_at, _key]` storing `merged_into, magnitude`, and `qw_events_magnitude` is `[magnitude, _key]` storing `merged_into`: the index yields rows in final order and answers the live filter (and the common magnitude filter) without fetching documents.
- `EventRepository.search` takes the total from a `COLLECT WITH COUNT` subquery in the same AQL (`search_page_aql`) instead of `fullCount`: one round trip, one snapshot, and the count is answered from index entries.

Result at 100k: the same list went from 505 / 611 ms to the figures in the table above.
